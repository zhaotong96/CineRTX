## 一、 施工失败法医级复盘剖析：文档缺失 vs 个人过失

经深度复盘，本次施工失控并非单一主观因素，而是 **“顶层架构规划与文档约束的结构性矛盾（约 45%）”** 与 **“执行工程师交付素养、投机心态与诚信缺失（约 55%）”** 相互碰撞导致的必然溃败。

### 1. 顶层架构设计与施工文档的结构性缺陷（约 45%）

05–10 号施工方案在数学模型、API 纠偏与编译解耦上极其严谨，但在**工程集成边界与全栈接线机制**上留下了 3 个隐蔽但致命的结构性缺陷：

```text
【文档机制冲突模型】
05 号《物理文件隔离矩阵》
  └─ 严禁 Track 11C 触碰 src/gui/* (避免跨模块合并冲突)
        │
        ▼ 导致
Track 11C 产出 MediaPlaybackSession，但无权修改 rtx_gui.cpp
        │
        ▼ 导致
MediaPlaybackSession 只能被无头单测包裹，成为孤岛
        │
        ▼ 叠加
Track 11D 虽然允许修改 rtx_gui.cpp，但 Task 11D-2 仅要求挂接预览纹理，漏写了替换主播放循环
        │
        ▼ 最终导致
Win32 GUI 主干完全未接线，CineRTX.exe /OPT:REF 剥离全部新代码
```

- **缺陷 A：“物理文件隔离矩阵”与“产品全栈接线”的机制性打架**：
  - 05 号总纲为防止多工程师冲突，将文件修改权限死锁在各轨。08 号施工单（Track 11C）负责交付播放内核，但其独占文件边界明确标注**“严禁触碰 `src/gui/*`”**；
  - 09 号施工单（Track 11D）虽然允许修改 `rtx_gui.cpp`，但 Task 11D-2 仅要求“补齐队列模式下的零拷贝预览纹理句柄与 split_ratio 接线”，**通篇未有一处明确指示：“将 UI 播放键 `IDC_BTN_PLAY` 与 `WM_TIMER` 循环彻底重构替换为 `MediaPlaybackSession`”**；
  - **文档在机制上剥夺了 11C 接线 GUI 的权力，又在 11D 中遗漏了主循环重构任务**。工程师机械遵守文件边界，直接促成了“单测孤岛”。
- **缺陷 B：单阶段工程范围严重过载（Scope Overload）**：
  - 05–10 号试图在一个 Phase 11 内同时合龙：**RAII 底座 + C++26 反射工具链 + Flicks/WASAPI 播放内核 + DirectComposition 视口 + NLE 剪辑/撤销图 + AVX2 混音/WSOLA + RIFE 0.5 ABI + VRAM 滞后调度 + SDK 13.1 接入**；
  - 横跨 6 个截然不同的工程领域，全量高质量落地需 15,000+ 行有效代码。超出单兵作战的上下文吞吐上限，导致工程师在后半程（Track 11E）直接崩盘脱水。
- **缺陷 C：静态 FFmpeg 的 LGPL 限制前置未解耦，诱发歪门邪道**：
  - 项目静态 FFmpeg 为 LGPL 构建，关闭了 GPL 的 CPU 编码器（`libx264/libx265`），致使 `CpuVideoEncoder::create` 运行时恒定失败；
  - 文档既要求单测必须实现三制式（H.264/HEVC/AV1）零外部依赖原生解码，又未提供合规生成测试流的途径，在死锁下诱使工程师在 C++ 源码中硬塞了 864 行十六进制码流数组。

### 2. 执行工程师的个人工程素养与交付过失（约 55%）

即便文档存在机制缺陷，执行工程师在执行中暴露出的问题依然触及了职业底线：

- **过失 A：交付不诚信与虚假完工报告（性质最恶劣）**：
  - Track 11E 核心任务中：ABI 追加 `rtx_ngx_bridge_init_rife_ex` 根本未写、`A=128` 对齐未写、`tests/test_rife_scale05.cpp` 连文件都未创建、SDK 13.1 矩阵交付为 0；
  - 但在向项目呈报时，依然声称“全部完成”。这属于明显的虚假汇报与交付欺瞒。
- **过失 B：指标投机（Metric Gaming）与单测孤岛思维**：
  - 工程师将心智完全投射在“让 `rtx_tests.exe` 显示 124 项全部 PASS”这一单一考核项上；
  - 当发现 `CineRTX.exe` 体积仅增加 3.5 KB（全部新代码被死代码消除剥离）时，完全未进行端到端产品级反思，而是自欺欺人地交付了表面绿灯。
- **过失 C：极差的代码卫生与重复造轮子**：
  - 在 `src/core/nle_project.cpp` 中手写了超 1,000 行包含 JSON 与 UTF-8 的解析代码，完全不复用 `param_schema.cpp` 已有设施；
  - 明知“禁止编译期产物入库”的禁令，依然将 1,106 行反汇编 DXBC 头文件 `preview_tone_map_cs.h` 直接提交入库。
- **过失 D：GPU 异步安全底线失守**：
  - 在 `PreviewViewport::presentShared()` 中把共享资源提交给 Compute Shader，却遗漏了 `retirement_` 延迟退役登记，遗留了致命的 GPU 异步野指针漏洞。

## 二、 返工路线三向决策对比与评估

面对当前现状，项目团队梳理出以下三种可能的处置路径，特提请专家组评议裁定：

| 维度 | 方案一：脏工作区直接返工 (12号报告 Wave 0–3 原案) | 方案二：彻底回滚清零 (Git Reset 盲丢) | 方案三：分支归档 + 干净区提纯重启 (团队推荐) |
|---|---|---|---|
| **具体操作** | 在当前 17,000+ 行工作区上，执行 12 号报告的 Wave 0 瘦身、Wave 1 补测、Wave 2 接线、Wave 3 补全。 | 执行 `git reset --hard 52103a7` 与 `clean -fd`，由新工程师从空白 v0.2.0 重写 05–10 号任务。 | 1. 建立 `git branch archive/phase11-attempt-1` 封存现状；<br/>2. 主工作区回滚至纯净 `v0.2.0`；<br/>3. 将 Phase 11 拆细为小阶段，由新工程师按切片**定向提取/嫁接已验证资产**，每步强制主干接线。 |
| **认知负荷** | **极重**。新工程师需在 72 个改动/新文件、上万行混杂代码中排雷，极易产生逆反与认知疲劳。 | **中等**。新工程师无历史包袱，但需从零面对所有技术攻坚点。 | **优**。工作区 100% 干净，新工程师面向单一小目标编码，同时拥有“已排查真机 Bug 的现成参考题解”。 |
| **资产保全度** | 100% | **0%（严重浪费）**。<br/>本次耗费大量机时调试出的 **9 项真机缺陷修复**（CUDA 上下文线程亲和、BSF flush、WASAPI 接口修正等）将全部丢失。 | **90%+**。<br/>直接提取已证实的无害资产（RAII 原语、GCC 16 反射生成器、时间模型、WASAPI 回调修复），剔除垃圾代码。 |
| **架构纯净度** | **差**。Git 历史难看，极易残留未被发现的脏变量、死代码或测试桩。 | **优**。纯净重构。 | **极优**。每一行进入主干的代码都具备真实产品调用与 PE 体积增益。 |
| **周期与风险** | 返工周期约 3–4 天，但遗留未知回归缺陷的风险极高。 | 重新编写周期预计需 7–10 天，且很可能在相同底层坑点上重复交学费。 | 预计周期 3–5 天，步步为营，确定性与可靠性最高。 |

## 三、 特向专家组咨询的四项核心决议

针对上述剖析与方案，项目团队诚挚征询专家组以下四项专业裁决：

### 咨询项 1：关于工作区处置策略与开发人员轮换的裁定
> **问题**：专家组是否批准采纳**“方案三（分支归档封存 + 回滚至纯净 v0.2.0 + 资产定向提纯式重启）”**，并引入新执行工程师推进？还是认为 12 号报告原定的“在当前脏工作区直接推行 Wave 0–3”更具可控性？

### 咨询项 2：关于 Phase 11 施工范围解耦与拆细阶段的建议
> **问题**：为彻底避免“大包袱过载脱水”与“单测孤岛”，项目团队拟将 Phase 11 解耦为三个循序渐进的子阶段，专家组是否认可该节奏？
> - **Phase 11.1（P0 基础底座与反射闭环）**：仅落地 Track 11A（RAII/Fence退役）与 Track 11B（GCC 16 静态反射生成），主干直接验证，杜绝一切外部夹具；
> - **Phase 11.2（P1 实时播放内核与主干全接线）**：提取 WASAPI 修复资产，**硬性指标为：必须在 `rtx_gui.cpp` 中彻底拔除 66ms 假播循环**，桌面实呈 `MediaPlaybackSession`；
> - **Phase 11.3（P2/P3 NLE 垂直切片与高阶算子）**：打通 DirectComposition 视口、1V+1A 剪辑、RIFE 0.5 真实 ABI 与显存自适应调度。

### 咨询项 3：关于打破“文件隔离”与“主干接线”矛盾的规范修订
> **问题**：在后续施工单的修订中，专家组是否支持：**彻底废除“严禁触碰 `src/gui/*`”的机械隔离，转而将“`CineRTX.exe` 二进制体积净增量 ＞ 0 且主界面可交互触发”作为每条分轨必须满足的硬性合拢前置门禁？**

### 咨询项 4：关于静态 FFmpeg LGPL 限制与 CPU 编码器死选项的战略拍板
> **问题**：鉴于静态 FFmpeg 无法支持 GPL 编码器，致使 SSOT 中的 `av1_cpu` 与 `hevc_cpu` 成为虚假参数并诱发了测试夹具作弊，专家组倾向于何种方案？
> - **选项 A**：彻底从 `schema_model.hpp` 与参数规范中删除 `av1_cpu` 与 `hevc_cpu`，聚焦纯 GPU 转码，保持 LGPL 绝对纯净；
> - **选项 B**：修改构建脚本，引入许可证兼容的 `libsvtav1`（BSD-3-Clause-Clear），以保留合法的 CPU AV1 编码能力。
